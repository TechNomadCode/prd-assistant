# Server code: rules for working here

## Plain Node imports
`scripts/load-notes.ts` runs `ai/providers.ts`, `env.ts` and everything they import under plain Node, which strips the types and runs the rest. In those files and their imports: relative imports with the `.ts` extension, no `@/` alias outside `import type`, and only TypeScript that can be erased (no `enum`, no parameter properties).

## The AI SDK (version 7)
Versions: `ai` 7.0.143, `@ai-sdk/openai-compatible` 3.0.71 and `@ai-sdk/react` 4.0.147, the releases that depend on exactly that `ai`'s `@ai-sdk/provider` (4.0.29) and `@ai-sdk/provider-utils` (5.0.62). Upgrade them together; `npm view <package>@<version> dependencies` shows what a release needs.

- **Version 7 names:** the system prompt goes in `instructions` (version 7 refuses system messages inside `messages`), `isStepCount` limits the model calls, `onEnd` replaces `onFinish`, and the standalone `toUIMessageStream({ stream: result.stream })` replaces `result.toUIMessageStreamResponse()`.
- **The chat model's interface** is the SDK's `LanguageModel`, specification v4 (`ai/chat-model.ts`). The type comes from `ai` itself, so the fake needs no extra package.
- **Failures** (`chat.ts`, `streamAnswer`):
  - A provider error, before the first word or partway, arrives as an error part: `streamText`'s `onError` logs it, and the stream carries on to its end.
  - A broken stream throws instead. `createUIMessageStream` catches it in `execute` and writes an error chunk; its `onError` logs it.
  - `toUIMessageStream`'s `onError` writes the text the browser sees, for stream errors and for tool errors. Only our own plain messages pass; anything else becomes one generic sentence.
  - An answer with no text and no error (a model that only reasoned, then stopped) gets an error chunk and a logged finish reason, so the visitor sees the error and "Try again" instead of nothing.
  - An answer cut off at the output limit (finish reason `length`) after some text gets an error chunk too, so a draft that stops mid-sentence doesn't look finished.
  - A saved section counts as an answer: one that saved a section and then wrote nothing gets no error, since the visitor sees the section.
  - A tool call the SDK can't read (input that fails the schema, a tool that's off, or one the chat doesn't have) arrives as `tool-input-error`. A call to one of the chat's own tools keeps that tool's part in the browser (`tool-saveSection`, `tool-searchNotes`), shown as a step that didn't work; a call to any other tool becomes a `dynamic-tool` part, shown as "A step". The model gets the SDK's own message, which says what to fix; the browser gets `describeError`'s plain sentence.
  - The SDK follows each refused call with a `tool-output-error` whose error is its message as a plain string. `describeError` can't place a string, so it returns the generic sentence, and the browser keeps the later chunk. `streamAnswer` gives that chunk the first sentence again (found 2026-10-18 in `node_modules/ai/dist/index.js`: `parseToolCall`, the `tool-error` case and `isDynamic`).
  - Each refused call is logged from `onStepEnd`'s `dynamicToolCalls`: the tool's name and why, either the tools on offer or the schema's complaints with their paths. Never the input, which may quote the visitor.
- **Tool budget:** `prepareStep` offers each tool only while it has tries left: three searches (`MAX_SEARCHES`) and two tries to save (`MAX_SAVE_TRIES`: one more for a section in the wrong form, or whose passages couldn't be read). Once a save works, and on the last call (`MAX_STEPS`), it returns `activeTools: []`, so the request carries no tools and the model has to write (https://ai-sdk.dev/docs/agents/loop-control). A tool that's off can't run even if the model calls it: each step parses and runs calls against its active tools only, and anything else is a `NoSuchToolError`. On staging (2026-10-17), gpt-oss ignored the prompt's limit, searched five times for one section and had no calls left for the reply.
- **Earlier answers in short:** `convertToModelMessages` turns the conversation's tool results into model input with the tools it's given, and `streamText` turns this answer's results with its own. So `forEarlierAnswers` hands the conversion a `searchNotes` whose `toModelOutput` keeps only each passage's id and interviewee, while this answer's own searches reach the model whole. The SDK's docs say to pass the same tools to both (https://ai-sdk.dev/docs/reference/ai-sdk-core/tool, `toModelOutput`); the difference here is on purpose, and `tests/unit/chat.test.ts` covers it. Saved sections keep their whole input, quotes included, so the model can revise one without searching again.
- **Output limit:** `maxOutputTokens` (4096) goes with every call; the package sends it as `max_tokens` (see Cloudflare below).
- **Tool errors:** the model gets the thrown error's message, so a refused query (`SearchQueryError`) lets it try again. Any other search failure is logged and replaced by `SearchFailedError`, so neither the model nor the browser sees internals.
- **Token usage:** `onEnd` doesn't run when a stream breaks, and after a failed call it reports only that call. So `onStepEnd` collects each finished call's usage, and the `finally` in `execute` logs the sum once per answer.
- **Retries:** the SDK retries a retryable provider error twice by default (`maxRetries`), every 429 included; `maxRetries` takes only a number, so the Cloudflare adapter stops the retries at the quota itself (Cloudflare below). The fake's failures are not retryable, or the retry would hide them.
- **Cloudflare's refusals in the browser:** `describeError` reads the last error inside the SDK's `RetryError`. `QuotaExceededError` becomes `QUOTA_USED_UP`, and any other 429 the retries didn't get past becomes `DEMO_BUSY` (both in `src/lib/chat.ts`). The browser recognises both by those exact words (`src/features/AGENTS.md`), so change them only there.
- **Reasoning:** gpt-oss streams its reasoning, and `toUIMessageStream` sends reasoning to the browser by default. `sendReasoning: false` keeps it on the server, so it never comes back with later messages either.

## Replayed answers (`ai/replay-chat-model.ts`, `ai/replays.ts`)
`npm run dev:replay` (slice 22) runs the dev server with `AI_CHAT_PROVIDER=replay` and `NEXT_PUBLIC_CHAT_REPLAY=1`, the header's "Replaying recorded answers" (`scripts/dev-replay.ts`, like `dev-real.ts`). It reads no token and sends nothing to Cloudflare; the environment guard allows "replay" for `AI_CHAT_PROVIDER` only, and `AI_PROVIDER` stays "fake", so the search keeps the fake embedder.
- **The copy:** `npm run replays:copy -- --from <measurement folder>` reads the measurement's records (git-ignored, so only the main checkout has them; from a worktree, pass the main checkout's folder) and writes `ai/replays.json`: per request, `REPLAYS_PER_REQUEST` counted runs without refusals or failed calls, those whose last call wrote words first, then by run. Each keeps the request's words (from `measurement/requests.ts`), the UTC day and every call's parts and `durationMs`, without `response-metadata` (Cloudflare's id and headers), the usage's `raw` and `providerMetadata`; a part of a type it doesn't know stops the copy. Each tool call gets the id `replay:<request>-<run>:<call>:<n>`. The copy of 2026-10-21 holds 18 runs of the baseline (prompt version 3).
- **Picking:** the first call of an answer compares the visitor's latest message with the recordings' words (NFC, lowercase, spaces collapsed) and gives that request's recordings out in turn, per server process (`picks`). Later calls find the recording by the answer's replayed tool call ids and play the next recorded call, so a search or save that ran here differently doesn't change what's replayed. An answer that began on the fallback stays on it; one whose recording has no calls left goes on with it.
- **Pacing:** each recorded reply arrives whole after its `durationMs` divided by `REPLAY_SPEED` (1 by default; the end-to-end tests use 100), as `simulateStreamingMiddleware` delivers Cloudflare's. A stop during the wait rejects with the signal's reason. Any other message gets the scripted fake with no delay between parts, after a recorded duration picked by the prompt's length.
- **What it can't show:** the searches return local passages, while the replayed words were written about staging's; a save's check runs here on the recorded statements. The check-in ("… looks right. Please draft …") has no recording, so it gets the fallback. The tools' budget and the prompt are today's, so a recording made under another setup may call a tool the chat no longer offers, and the SDK refuses it as it would the real model's.
- **The scenario tour** (slice 24, `ai/scenarios.ts`; the steps and their words in `src/lib/scenarios.ts`, which the browser's panel shares): scripted answers written as recordings (`S-<step>`, recorded "scripted"), which the replay gives out by their words like any other, after their own waits, never the real ones'. Their searches, saves and the check run here for real, so each scripted citation says whether the check should confirm it (`passes`, dropped before the model's tool input) and `tests/unit/scenarios.test.ts` holds them to the interviews. A scripted call may fail instead (`fails`): "before" and "busy" throw a non-retryable `APICallError` (503, and 429, which `describeError` words as `DEMO_BUSY`), "partway" streams the reply's first eight words one read at a time and then errors (a stream's `error()` drops what waits in its queue, so enqueuing them all first lost the words: found 2026-10-21), and "quota" throws `QuotaExceededError`. The first three fail once per server process (`failed`), so "Try again" works; the quota fails every time, as Cloudflare's would. Not retryable, so the SDK's own retries never play a failing call again.
- **Never in a deployment:** `loadReplays` reads the file at run time from `process.cwd()` with `turbopackIgnore`, so builds neither trace the project for it nor carry it (the build's own warning, 2026-10-21), and `NEXT_PUBLIC_CHAT_REPLAY` is inlined only where it was set when Next.js compiled (Next.js, *Environment variables*, read 2026-10-21 through Context7).

## The system prompt (`prompts/system-prompt.ts`)
- **Source:** a copy of the toolkit's PRD prompt with the traceability rules of its research prompt, both at the toolkit's commit cb7956e (links in the file). The file's header says what was kept, changed and added; `docs/plan.md` (slice 4) lists the rules it must hold.
- **Versions:** any change to the text, even a comma, gets the next `version` and its SHA-256 fingerprint in `FINGERPRINTS` (`tests/unit/system-prompt.test.ts`). The test fails until both are there; earlier fingerprints stay, so no number is used twice. Version 4 moved the tools' wording into this file and repeated the writing rules there; it saved nothing on staging (2026-10-18), so the prompt went back to version 3. The owner tries a new version on staging before it ships; it's measured against the baseline first (*Judging the model's behaviour*, below), the measurement doesn't block launch, and since 2026-10-19 a reworded prompt is a measured change like any other (`docs/decisions.md`).
- **Trying a change:** `npm run dev:real` runs the chat on the real model here, with this machine's token from `.env.development.local` (the owner's exception, 2026-10-19; `scripts/dev-real.ts` sets `AI_CHAT_PROVIDER=cloudflare` for the dev server, and `env.ts` lets it pick the chat model's adapter apart from `AI_PROVIDER`). The search keeps the fake embedder, so which passages come back differs from staging. Follow *Judging the model's behaviour* below, its budget included. Cloudflare's page for gpt-oss-20b links no playground (checked 2026-10-17), and a playground couldn't run `searchNotes` anyway.
- **Plain text:** the prompt asks for no Markdown and uses plain labels itself, since a model copies the style it's given. The chat renders bold, inline code and lists anyway and removes every other mark (`src/lib/markdown.ts`), because gpt-oss-120b wrote `**` regardless; statements in the PRD stay plain text.
- **Searches and saves:** the prompt says the model has three searches a reply, after which the search is switched off, and saves once a reply, after which the tools are off. `MAX_SEARCHES` and `prepareStep` in `chat.ts` enforce both. Change them together.
- **Tokens:** every model call sends the whole prompt, about 1,290 tokens at four characters a token (version 3: about 1,775, about half of each request in the baseline; version 2: about 1,575; the short prompt before it: about 190), plus the two tools' definitions. A drafted section takes at least three calls: a search, the save and the reply. Keep it tight.

## Judging the model's behaviour
The owner's decision of 2026-10-19 (`docs/decisions.md`, External services): the model's behaviour is measured, not diagnosed from single runs.
- **Observations, not causes.** gpt-oss answers differently on every run, so one run shows what can happen, not how often or why. Record what was seen with the setup below and the number of runs. Name a cause only once a comparison has isolated it, and propose no fix for a cause nobody has isolated. Model behaviour isn't tracked in `KNOWN-ISSUES.md`.
- **Baseline first.** Before changing anything that shapes the model, measure the current setup on fixed requests, several runs each, with every run's trace and setup saved: the measurement tool, slice 9 reworked (`docs/plan.md`). Then change one variable, write down the expected effect, rerun the same requests the same number of times and compare.
- **Free checks first.** Much can be checked without the model: the request bodies our code sends, the provider's input schema, a recorded reply replayed through our code. Spend neurons only on what only the model can answer.
- **Recorded replies as fixtures.** When a real reply shows how our code handles the model's output, keep it as a test fixture, so the fix is tested for free.
- **The budget.** Every real-model run draws on the daily free allocation of 10,000 neurons, which staging shares and production will after launch (`docs/decisions.md`). Before a run, say how many answers it sends and roughly what they cost. The server logs each answer's tokens, and the rates per million tokens are in `docs/decisions.md` (External services, gpt-oss-120b). Measured on staging (2026-10-18): about 313 neurons for a first section and 555 for a second answer. Locally with the fake search (2026-10-19, the smoke test): 284 and 1,014, the second after three searches, a refused fourth and six calls. Single runs, so expect a second answer anywhere up to about 1,000; later answers cost more, because every call resends the conversation. Prefer requests of one answer, and the fewest runs that can show a difference. The measurement stays on the Free plan (`docs/decisions.md`, External services, 2026-10-19): a batch may use what's left of the day, which the owner says since staging shares it, and a quota refusal stops the batch until the next UTC day; the estimate is `docs/records/measurement-estimate-2026-10-19.md` (local). Outside the measurement, nothing runs on the real model without asking. Careful all the same (the owner, 2026-10-19), because a careless agent can spend a day's allocation in minutes:
  - Every run has a purpose written down before it starts: the baseline, or one change with its expected effect.
  - Free checks first; the fake model for anything about our own code.
  - One run at a time on this machine, across all sessions; never start runs in parallel.
  - Never rerun to get a better result. A run is rerun only when it couldn't count (a broken setup, "not run"), and the rerun is announced like any run.
  - No probes (the owner, 2026-10-20): every real-model request is a run of a measurement, sent to measure the model's behaviour, never to see whether Cloudflare accepts requests again. After a refusal, wait for the next reset or the owner's word, then send the planned runs.
  - Before a run, say how many answers it sends and roughly what it costs; stop and report when it costs half as much again as announced.
  - After each run, report its neurons and the running totals for the day and the month.
- **A stop rule.** Launch needs only the grocery delivery request to pass (`docs/decisions.md`, Launch). A change to what shapes the model ships only if it beats the baseline without worsening another rule: measured on the grocery delivery request alone, then on the full set before it ships (`docs/decisions.md`, External services, 2026-10-19); what remains is reported in the README.
- **The simpler flow** (`docs/decisions.md`, External services) is one candidate, measured like any other change.

- **Reasoning between tool calls:** gpt-oss's response format says its chain of thought must be passed back while it calls functions, and dropped once it has given a final answer (https://github.com/openai/harmony/blob/main/docs/format.md, "Handling reasoning output in subsequent sampling", read 2026-10-19 through Context7). `@ai-sdk/openai-compatible` 3.0.71 sends an assistant message's reasoning parts as `reasoning_content` (`dist/index.js`). The package code shows that an answer's later calls carry its earlier calls' reasoning (`ai/dist/index.js`: a step's reasoning parts stay in its response messages and in their conversion; read 2026-10-19), while earlier answers carry none (`sendReasoning: false`); not yet seen in a request body. Whether Cloudflare's endpoint uses `reasoning_content` is unchecked.
- **The fake search and the two claims:** it ranks by shared words only, so a question that shares no word with any passage, such as "dark mode" or "grocery delivery", ties every passage at distance 1 and gets five unrelated ones. Henk's "Black on white or white on black" comes back only for a question that says "black" or "white" (checked 2026-10-19 with the fake embedder and the loader's parser, no model). So locally the dark mode claim meets Henk's words only if the model's own question names a colour, and the grocery delivery claim gets passages unrelated to it.

## The measurement (`measurement/`)
The tool that measures the model's behaviour (`docs/plan.md`, slices 9a to 9c; design in `docs/records/measurement-estimate-2026-10-19.md`, local).
- **The recorder** (`recorder.ts`, 9a) hooks in without changing `chat.ts`: `recorder.fetch()` goes into `CloudflareSettings.fetch` and keeps each HTTP attempt (the body sent, the status, the reply's headers without `set-cookie`, the reply's body with Cloudflare's id, usage and `reasoning_content`, timings), and `recorder.wrap(model)` keeps the AI SDK's view of each call (its settings without the conversation, the tools' names and fingerprint, every part of the reply with each run of deltas joined, the error). It works on the fake model too, which never calls `fetch`. One recorder per answer.
- **Never the token:** request headers are never kept, and the account ID in the address becomes `<account>`. `records.ts` then refuses a whole record that holds the token (also as JSON escapes it) or "bearer " in any case, writes nothing and never repeats either. It never overwrites a file (`wx`): an existing record is an earlier run's.
- **Before the answer:** `measureAnswer` checks the request's name, the run number and the passages' fingerprint, and reads the code's state and the versions (`startSetup`) before the model is called, so a broken setup fails without spending neurons. The rest comes from the recorded calls (`finishSetup`).
- **Whole replies only:** a model call's `error` is recorded only when `doStream()` itself throws. A stream that broke partway would leave a call without `error` or `durationMs`; it can't happen while Cloudflare's replies arrive whole (below), so recheck this before streaming returns.
- **Retries:** the AI SDK retries by calling the model again with fresh settings (`ai/dist/index.js`, `retry(() => model.doStream(…))`), so a retry is the model call after one with an `error`, not a second HTTP attempt.
- **The setup** (`setup.ts`): the model as called and as Cloudflare named it, the prompt's version and SHA-256, the first call's tools fingerprint (SHA-256 of their JSON with sorted keys, the same on the fake), the generation settings in the first request body, the commit plus `git status --porcelain` and a fingerprint of the uncommitted changes in `src`, `scripts`, `package.json` and `package-lock.json`, the search and its passages' fingerprint (from the runner), the versions of `ai`, `@ai-sdk/openai-compatible` and Node, the time and the run.
- **A measured answer** (`answer.ts`): `measureAnswer` runs `streamAnswer` with the wrapped model and keeps the UI stream's chunks (searches, saves and the check's results). The conversation must have passed `readChatRequest` first; its fingerprint in the record covers the request's own words and the saved conversation it continues, so a changed text shows there. Records go to `docs/records/measurements/<measurement>/<UTC date>/<request>-<run>.json` (`recordPath`, with the measurement's folder as its root).
- **The command** (9b): `npm run measure -- --name <measurement> --purpose "<why>"`, with `--runs` (5), `--requests`, `--conversations-from <measurement>` and `--plan`, which prints the plan and sends nothing. `npm run measure:fake` runs the same tool on the fake model and embedder into `docs/records/measurements-fake/`, with no token and no ledger. A *run* is one answer to one request; a *batch* is one command. `cli.ts` reads `.env.development.local` itself (`parseEnv`), only for a real batch that isn't a plan, and only when started as `npm run measure` (`npm_lifecycle_event`), so the guard ran first with `--measure`; the token goes to the Cloudflare adapters and `writeRecord`, never into `process.env`, so `git` in the setup doesn't inherit it.
- **Plain Node with hooks:** `chat.ts` and the prompt use `@/` and `server-only`, so `scripts/measure.ts` registers `scripts/server-imports.ts` first: Node's synchronous `registerHooks` maps `@/` to `src/`, adds a missing `.ts` inside `src/`, and gives `server-only` its empty module, as `vitest.config.ts` does. No new dependency.
- **The search's copy** (`passages.ts`): the passages of `notes/`, parsed with the loader's parser and embedded with the loader's `embeddingInput` and `contentHash`, kept in `<root>/passages.json`; a passage is embedded again only when its hash changes. `rankPassages` orders by cosine distance, then id, as `search_passages` does, and `copySources` gives the chat the app's own `searchInterviews` over it and the cited passages from it, so neither the database nor the local stack is needed. Ids count from 1 in file order; they differ from the database's, which matters only for exact ties.
- **The requests** (`requests.ts`): A to E as the estimate's appendix C has them; A and D take their words from `src/lib/suggestions.ts`, which the intro screen (slice 7) uses too. Changing a text means a new baseline for its request.
- **Saved conversations** (`conversations.ts`): D and E continue the first counted run of A with every quote confirmed and no error; C2 the first counted run of C1 whose reply has a sentence with "?" and a word about the connection (offline, signal, reception, connection, connectivity, internet), an approximation 9c reads by hand. Each is the run's conversation plus its answer rebuilt from the recorded chunks with `readUIMessageStream`, saved once (`wx`) in `<measurement>/conversations/`, fingerprinted and refused if it changed; every conversation passes `readChatRequest` before an answer. A continuation waits, and is skipped, until its conversation exists; `--conversations-from` takes another measurement's, so a comparison starts from the baseline's; it defaults to `--compare-with`'s, and a measurement that names itself there (a flow change) saves its own.
- **The meter** (`budget.ts`): every Cloudflare request goes through it under the recorder. It counts each reply's `usage` at gpt-oss-120b's rates and each embedding request at the loader's token bound (Cloudflare reports none), spaces requests a second apart (300 a minute allowed), and once the batch has spent more than its cap it sends nothing more and throws `BudgetExceededError`, which the AI SDK doesn't retry (`handleFetchError` in `@ai-sdk/provider-utils` passes it through). The cap is 1.5 times the expected neurons of the answers that can go now (each request's mean in this measurement once it has a counted answer, else in the one it's compared with, since a change can move the cost: `reasoning-high` cost about twice `prompt-v5`'s and its first batch was cut at a cap set from the whole ledger, 2026-10-21; otherwise its mean so far in the ledger, or the estimate's 300, 450 and 785) and the copy; an answer waiting for its saved conversation raises the cap by 1.5 times its expectation only once that conversation exists and only for runs still to come in the batch (earlier ones were skipped at their turn, and the closing line names them for a later batch), and the plan says how far it can rise. Without that, waiting answers that never go would loosen the cap for the rest (the review, 2026-10-19).
- **Outcomes:** a 429 with code 3036 or 4006 (quota: the errors page names 3036, the `/ai/v1` endpoint sent 4006 with the same message on 2026-10-20), code 3040 (busy) or any other 429 (per-minute) that no retry got past makes the answer "not run". The AI SDK retries a refused request as it was, so the meter counts a refusal as recovered only when the same request (address and body) later succeeds; a refused search stays unrecovered when the chat carries on or the model searches again with other words. A recovered answer counts, and its record keeps every refusal. A "not run" answer's record goes to `<measurement>/not-run/<date>/`, and quota stops the batch; a per-minute refusal pauses a minute. An answer cut off at the cap is "not run" too, and the batch stops. A record `writeRecord` refuses is "not recorded": nothing is written, its spend still counts. Only a counted answer fills its run (`<measurement>/<date>/<request>-<run>.json`); a later batch sends the others again and says so in its plan.
- **Measured commits:** each record names the commit it ran on (`setup.code.commit`), and the comparison runs `git diff` on those. GitHub's rebase merge gives a branch's commits new ids, which leaves the recorded ones on no branch, where Git may clean them up once the reflog expires (90 days by default). So after each merge, tag every commit the records name that isn't on `main` as `measured/<short id>`; these tags stay local.
- **The ledger** (`<root>/spend.jsonl`, real batches only): one line per answer and per copy, for the totals of the UTC day and the UTC calendar month, which may not match the billing month. Checked against Cloudflare's dashboard on 2026-10-19: the chat's neurons matched (6,207 against about 6,220), and the embedding bound was about twice the real figure. The dashboard's "used today" lagged by about an hour, and the daily limit let the day reach 10.4k before refusing, so size a day's batch to what's left by the dashboard and the owner, with room to spare.
- **Scoring** (`score.ts`, 9c): each counted run on the product description's rules, from this answer's saves only (`savedSections`: the `saveSection` calls that worked). `RULES` names each rule and the requests it applies to: `quotes` and `cites` on all; `saves-first` on A; `asks` on C1; `cites-answer` on C2 (a confirmed chat citation of `visitorMessageId`, `visitor-2`); `both-views` on B ({maya-3, henk-4} against {daan-5, sofia-5, sofia-6}, on different statements, plus a statement starting "Open question" or in Open Questions); `no-claim` on D and E. A verdict is pass, fail or "saved nothing", which is never a pass: for A's `saves-first` it's a fail, and `asks` needs no save. Where code only approximates a rule (`asks`, `cites-answer`, `both-views`, `no-claim`), the rule says what to read by hand and the score lists it. Faults use the PRD's own wording (`objection` and `NO_QUOTE` in `src/lib/prd.ts`), plus one for an interview among the sources of a delivery or dark mode statement.
- **The report** (`report.ts`, 9c): `npm run measure:report -- --name <measurement>` (`--fake` for `measurements-fake/`) reads the records only, so it needs no token. It prints "k of n" per request and rule with "saved nothing" apart, the setup's parts and whether they differ between runs, the spend with "not run" and "not recorded" (from the ledger) apart, each answer's time and how many took longer than 60 seconds, the statements at fault, and what to read by hand with each reply once; it also saves it as `<measurement>/report.md`.
- **A comparison** (9c): `--compare-with <measurement>` and `--target <request>:<rule>` (repeatable) go into `measurement.json` with the purpose before the first answer, and a later batch under that name must repeat them. The report then tests each target with a one-sided Fisher's exact test at 5% (hypergeometric, computed in `fisherOneSided`; at five runs each, 0 → 4 gives p = 5/210), flags any other request and rule that dropped by two runs or more on the change's number of runs, and warns when more than one part of the setup differs: model, prompt, tools, generation settings, code, search, libraries, saved conversations. Code is compared at report time with `git diff --name-only` over `src/server`, `src/lib` and `package-lock.json`, leaving out the measurement tool and the prompt file (its own part), since every change moves the commit. A change to the tools' descriptions shows as tools and code (`chat.ts`); the report lists the files, so read them before trusting the warning.
- **One batch at a time:** a lock file in the system's temporary folder (`lock.ts`), shared by every checkout and worktree; a lock whose process has ended is taken over.
- **Logs:** what the chat logs during an answer is kept in its record, not printed, and checked with the rest before it's written.
- **gpt-oss-120b's input schema** (`sync-input.json`, read 2026-10-19): `temperature` (default 0.6), `top_p`, `top_k`, `seed` and the penalties, but no `reasoning_effort`; a message names only `role` and `content`, though `tool_calls` work, so the schema doesn't settle whether `reasoning_content` is read.
- **Sources (read 2026-10-19, through Context7):** for the runner, Node's `module.registerHooks` (https://nodejs.org/docs/latest-v24.x/api/module.html), `process.kill(pid, 0)` and the AI SDK's `readUIMessageStream` (https://ai-sdk.dev/docs/reference/ai-sdk-ui/read-ui-message-stream); for the recorder, language model middleware, `wrapStream` with a `TransformStream` (https://ai-sdk.dev/docs/ai-sdk-core/middleware) and the installed `LanguageModelMiddleware` type; Node's `crypto.hash`, the `wx` flag and `execFileSync` (https://nodejs.org/docs/latest-v24.x/api/); for the comparison's options, `util.parseArgs` with `multiple: true`, which collects a repeated option into an array (https://nodejs.org/docs/latest-v24.x/api/util.html).

## The citation check (`citations.ts`)
- **The right words:** an interview quote is checked against the cited passage's `answer` only, never its `question`. The passages come from the database with the read key (`db/passages.ts`: the cited interviews by slug, then the cited positions), never from search results the browser sends back. A chat quote is checked against the request's user messages only, never the assistant's. Those come from the browser, so a visitor can only confirm their own words.
- **Matching:** NFC, lowercase, every quote mark as one, spaces collapsed; punctuation and spaces are stripped from the quote's ends only; whole words only, and an apostrophe between letters joins one word, so "don" isn't in "don't". Never loosen it (`docs/decisions.md`, Data): when a model keeps failing it, the prompt or the model changes.
- **Sources as written:** a source is trimmed and lowercased. `chat` (`CHAT_SOURCE`) means the visitor; anything else that names no passage is `unknown`, and unverified.
- **What the model learns:** `checkReport` in `chat.ts` sends the counts, each unverified quote with its problem, and the statements that cite nothing, numbered from 1.
- **Shared types:** `src/lib/prd.ts` holds the nine sections, the draft and checked shapes, `isFlagged`, `tally`, `isVisitorDecision` and `sourcesOf`, which the browser uses too. The check itself is `server-only`.
- **For the pop-over:** a checked interview quote carries the passage's `question` and `answer`, read with the check, so the browser can show the quote in its full answer. The model never sees them: it gets `checkReport`, and earlier saves reach it through the same `toModelOutput`.
- **Limits:** the input schema bounds statements, citations and lengths: roomy for a model, tight for a forged request. The output schema checks saved sections the browser sends back with later messages.

## Cloudflare Workers AI (`ai/cloudflare.ts`)
- **The chat model** is `@cf/openai/gpt-oss-120b` since 2026-10-18 (`ai/models.ts`, `docs/decisions.md`); gpt-oss-20b before. Their input schemas (`sync-input.json`) were identical byte for byte that day, so the workarounds below, found with gpt-oss-20b, apply unchanged. Its behaviour is measured as *Judging the model's behaviour* describes.
- **Endpoint:** `createOpenAICompatible` with `baseURL` `https://api.cloudflare.com/client/v4/accounts/<account ID>/ai/v1` and the token as `apiKey` (sent as `Authorization: Bearer`). Chat goes to `/chat/completions` (`chatModel`), embeddings to `/embeddings` (`embeddingModel`). Settings: `CLOUDFLARE_ACCOUNT_ID` (32 hexadecimal characters, checked in `env.ts`) and `CLOUDFLARE_API_TOKEN`.
- **Whole replies for chat:** streamed, Cloudflare sends gpt-oss's tool call as `reasoning_content` text (the bare JSON arguments, no tool name, no `tool_calls`) and ends with `finish_reason: "stop"`, so the search never runs (staging, 2026-10-17; raw stream in `docs/plan.md` history). Whole replies carry proper `tool_calls`, as the owner's first test showed. `createCloudflareChatModel` wraps the model in `simulateStreamingMiddleware` (https://ai-sdk.dev/docs/reference/ai-sdk-core/simulate-streaming-middleware), so `streamText` still works and each reply arrives in one piece. Cloudflare's own `workers-ai-provider` 4.0.0 also falls back to non-streaming for gpt-oss. Recheck before streaming again.
- **Text in every message:** Cloudflare's input schema requires each message's `content` to be a string or a list of text parts (`sync-input.json` of the model). The package sends `content: null` on an assistant message that only calls a tool, so the follow-up after a search got 400, code 5006 (staging, 2026-10-17). `withTextContent` in `transformRequestBody` sends `""` instead.
- **256 output tokens by default:** the model's `max_tokens` defaults to 256 (`sync-input.json`), and gpt-oss's reasoning counts against it. On staging (2026-10-17), section drafts stopped with finish reason `length` before any text, so `chat.ts` asks for 4096. The schema states no maximum; the context window is 128,000 tokens.
- **No tool choice:** the schema has `tools` but no `tool_choice`, so the chat stops the search by leaving the tools out of the request rather than sending `tool_choice: "none"`. The schema allows a request without tools, even after tool calls in the conversation. On staging (2026-10-18), the reply after a save, sent without tools, came back as text. A request without tools doesn't guarantee words, though: with prompt version 4 the same day, gpt-oss called `searchNotes` twice after it was switched off, the second time on the last call, which carried no tools, and the answer ended without words.
- **The quota and other 429s** (slice 8a): `refusingQuota` wraps `fetch` for chat and embeddings alike, under whatever `fetch` the settings pass (the measurement's meter and recorder see every reply first). A 429 with code 3036 or 4006 (`QUOTA_CODES`; 4006 is what `/ai/v1` sent on 2026-10-20) throws `QuotaExceededError` from `fetch`, which `handleFetchError` in `@ai-sdk/provider-utils` passes through and the SDK doesn't retry: nothing works before 00:00 UTC. Any other 429 (the per-minute limit, code 3040 out of capacity) goes on to the SDK's two retries, but a `retry-after-ms` or `retry-after` asking for more than `MAX_RETRY_WAIT_MS` (5 seconds) is dropped first, so the SDK's own 2 and 4 seconds apply instead of up to 60 each, inside the route's 60 seconds (`getRetryDelayInMs` in `ai/dist/index.js`, read 2026-10-20). The request bodies are untouched. The quota codes are also in `measurement/budget.ts` (`QUOTA_CODES`); keep the two lists the same. Replayed replies in `tests/unit/cloudflare.test.ts`; the 4006 one is Cloudflare's own of 2026-10-20.
- **`includeUsage: true`** makes streamed replies report tokens; kept for when streaming returns.
- **No token count for embeddings:** on staging (2026-10-17) Cloudflare's `/embeddings` reply had no `usage`, and the AI SDK then reports `NaN` tokens. `cloudflare-embedder.ts` logs "Cloudflare reported no token count" instead.
- **Embedding batches:** Cloudflare's bge models take at most 100 texts a call; the package would send 2,048, so `cloudflare-embedder.ts` splits them.
- **512 input tokens:** the docs don't say whether a longer text is refused or cut. `ai/embedding-input.ts` bounds the tokens without a tokenizer (lowercase, remove accents, count non-space characters, add the two markers) and refuses any text over 512 before a call. The loader names every passage over the bound and loads nothing.
- **Pooling:** the OpenAI-compatible endpoint uses the model's default, `mean`. Cloudflare suggests `cls` for long inputs, but the two can't be mixed: switching means re-embedding every passage and changing the query side too.
- **Tests:** `CloudflareSettings.fetch` takes a recording fetch, so `tests/unit/cloudflare.test.ts` checks the requests with no network. Real calls happen on staging, and here only through `npm run dev:real` and `npm run measure`.
