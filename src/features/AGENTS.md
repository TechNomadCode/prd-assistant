# Browser features: rules for working here

## The chat and the PRD (`workspace/`, `chat/`, `prd/`)
- **One conversation, two panes:** `workspace/workspace.tsx` owns `useChat`. The PRD is built from the conversation, the latest `saveSection` result per section (`savedSections` in `src/lib/chat.ts`); nothing else changes it. "Start over" stops the answer, clears the messages, the error and the check-in, and brings the intro back.
- **The check-in** sends "<latest section> looks right. Please draft <next>." as the visitor's message, where the next is the first section in the PRD's order not drafted yet. It counts as arrived once a save of that section comes after the message it sent; until then it gives way, while the assistant works, to that section's own "Drafting…", and comes back after a failed or empty answer.
- **What the PRD shows changing** (slice 13): "Drafting…" sits beside the heading of each section being drafted while the assistant works (`sectionsBeingDrafted` in `workspace/workspace.tsx`): the check-in's section from its message until it arrives, and any section whose save has started in the answer on its way. It's a sibling of the `<h3>`, not inside it, so the heading's and the region's names don't change, and it carries `.shimmer`. A section saved, or saved again with different statements (compared as JSON), lights up: a decorative `span.just-changed` behind it, remounted with a new `key` on each change so the fade restarts without touching the heading's focus, a white tint fading to transparent in 2s, which runs with reduced motion too, since a fade doesn't move. The sections the PRD mounts with, such as those brought back after a reload, and a save that changes nothing, don't count (`useChanges` in `prd/prd-document.tsx`, React's "storing information from previous renders" pattern). The title line's count rolls (`RollingNumber`, `.roll` in `src/app/globals.css`): plain text at rest, so a text query still finds the whole line; during a change the old number leaves and the new one comes in, clipped with `clip-path: inset(0)`, since `overflow: hidden` would move an inline block's baseline (MDN, `clip-path`, read 2026-10-20 through Context7). With reduced motion the old number is `display: none` and no `animationend` comes, so the rolling markup stays until the next change. jsdom has no `AnimationEvent`, so React listens for a vendor-prefixed event there; `tests/unit/animation-event.ts` defines one before React loads.
- **Desktop layout:** the body takes the viewport height only on pages that hold `[data-workspace]` (`lg:has-[[data-workspace]]:h-dvh` in `src/app/layout.tsx`, Tailwind's `has-*` variant), so the two panes scroll on their own and the transcripts page scrolls as before. On those pages the page is at most 1600px wide (`max-w-workspace`, from `--container-workspace` in `src/app/globals.css`), and the chat's column is `clamp(25rem, 38%, 32.5rem)`: 400px on a 1024px screen, 520px from about 1416px, with the PRD taking the rest (`docs/decisions.md`, Design, 2026-10-20). The header, the main area's padding and the footer take 114px of the height. The header is 45px on every page, not only the workspace, so it doesn't change height when the intro gives way to the chat; the focused skip link fits inside it. `tests/e2e/layout.spec.ts` measures all of it.
- **The typeface** (slice 18): Inter, through `next/font/google` in `src/app/layout.tsx` (Next.js 16, `next/font`, read 2026-10-21 through Context7): its files are downloaded at build time and served from `/_next/static/media/`, so the visitor's browser never asks Google, and the build needs Google Fonts to be reachable. Its licence is the SIL Open Font License 1.1 (https://github.com/rsms/inter, `LICENSE.txt`, read 2026-10-21), which allows bundling it with software. `variable: "--font-inter"` on `<html>` puts it first in `--font-sans` (`src/app/globals.css`, in `@theme inline`, so the variable resolves where it's used: Tailwind, *Theme variables*, read 2026-10-21 through Context7), with the system fonts behind it in case it fails. Inter is variable, so 400, 500 and 600 come from one file. Against a jump, Next adds "Inter Fallback", `local(Arial)` resized to Inter's metrics, shown until Inter arrives. On Windows Chromium, with Inter held back, the transcripts page grew 20px of 7,216 when it arrived, against 72px with plain Arial, and the layout-shift score stayed near 0 in both, as the top of the page barely moves; so `tests/e2e/pages.spec.ts` checks the fallback's form, not a measured jump. Where Arial isn't installed (Linux, Android), the fallback is the system's font, unresized.
- **The chat's spacing:** 16px from a question to its answer, or to "Thinking", and 32px between turns (`docs/decisions.md`, Design, 2026-10-20), through `data-role` on the conversation's items: a question that got no answer stays 32px from the next one. Inside an answer, 8px between steps in a row and 16px between a step and text either way (`spaceAbove` in `chat/conversation.tsx`, opencode's rule in `packages/session-ui/src/timeline/projection.ts` at 50c5fce, read 2026-10-20), and 24px before a failure notice, in the answer and above the chat's alert.
- **The moving line** (slice 11): while an answer is on its way exactly one line moves, the latest step in progress, or "Thinking" (slice 20, below) at the answer's end whenever no step runs and no reply arrives. Text at the answer's end counts as arriving even once its part is `done`, and so does a thought's time, which comes just before its reply: a reply's steps come after its text, so trailing text means the answer is finishing, and a "Working…", as the line read then, that flashed there before the stream closed left the chat 48px off its end, so it stopped following when the message box grew (found 2026-10-20 by `tests/e2e/layout.spec.ts`). Nothing moves once the status leaves `submitted`/`streaming` (`activityOf` in `chat/conversation.tsx`). The band is the one shared class `.shimmer` in `src/app/globals.css`, for slices 13, 15 and 20 to reuse: a gradient clipped to the text, only under `prefers-reduced-motion: no-preference` and `forced-colors: none` and where `background-clip: text` is supported, so everywhere else the line is still and grey (MDN, `background-clip`, Accessibility, read 2026-10-20 through Context7). It is decoration: the screen reader's status line in `chat/chat.tsx` is unchanged. jsdom applies no media queries, so the unit tests check which line carries `.shimmer`, and `tests/e2e/chat.spec.ts` checks the animation and the still line with `page.emulateMedia({ reducedMotion })`.
- **The search lines** (slice 15, `chat/search-step.tsx`, `chat/search-run.tsx`): opencode’s form at 50c5fce (`docs/decisions.md`, Design, 2026-10-20). Each search is a plain `<p>`, never a button: "Search" in medium weight, the query and what came of it in grey, 13px, one line cut off with `truncate` (a failure keeps its whole reason). The dot is `aria-hidden` and an `sr-only` "passages from" goes before the names. Searches in a row (`laidOut` in `chat/conversation.tsx`) fold into `SearchRun`: a button "Used 3 searches" with `aria-expanded`, whose count is the shared `RollingNumber` (`src/components/rolling-number.tsx`, also the PRD’s), then an inline SVG triangle, `-rotate-90` and `opacity-45` at rest, full on hover and turned down when open, through Tailwind’s `group-aria-expanded:`; its lines sit in `.fold` (`src/app/globals.css`), a one-row grid from `0fr` to `1fr` with `visibility` held back until the slide ends, and `inert` while closed, which takes them out of the accessibility tree and the tab order (MDN, `inert`, read 2026-10-20 through Context7). The box that clips them is positioned: the lines' `sr-only` labels are `absolute`, and placed against the chat's pane they escaped the clip and stretched the pane below its last line while a folded line was the answer's last (found 2026-10-22). Interpolating the row from `0fr` was checked in Chromium only (2026-10-20); where it doesn’t interpolate, the lines appear at once. Rows are `leading-7`, 8px apart, 4px under the button. While a run’s search runs, the run’s span carries `.shimmer`, and its white parts drop their colour, since `text-foreground` would cover the band. The fake model searches three times when a message holds `FAKE_SEARCH_AGAIN`, which the end-to-end tests use. A run takes in the thought lines (below) in its unbroken stretch of searches and thoughts, before, between and after the searches, as opencode's `groupContent` does; a stretch with one search stays plain lines, and the count counts searches only.
- **How long the model thought** (slice 20, `chat/thoughts.ts`, `chat/thought-line.tsx`): opencode's form at 50c5fce (`docs/decisions.md`, Design, 2026-10-21): "Thinking" while it thinks, 13px medium on a 16px line with `.shimmer`, then "Thought" in medium weight and white with the time in grey and tabular figures, as "Thought 8s", and from a minute "1m 5s", whole seconds rounded (opencode's `AssistantReasoningContent` in `packages/session-ui/src/message/message-content.tsx` and its words in `packages/ui/src/i18n/en.ts`, read 2026-10-21). The line doesn't open. The server can't time the reasoning, since the chat model's replies arrive whole, so the browser times each wait for a reply: `TimedTransport` in `workspace/workspace.tsx` pipes each answer's stream through `timeThoughts`, which starts the first wait at the request and each later one when the last step running finishes (a tool output), and puts a `data-thought` chunk with `{ ms }` just before the chunk that begins the next reply (text or a tool's input). The AI SDK keeps it as a part of the answer in that place (any `data-*` chunk without `transient`, ai 7.0.143, `processUIMessageStream`), so it's stored and restored with the conversation; a wait the answer ends in, stopped or failed, gets none. The parts go back to the server with the conversation, where `safeValidateUIMessages` accepts any `data-*` part and `convertToModelMessages` drops it unless given `convertDataPart`, so the model's input doesn't change (`tests/unit/chat.test.ts` compares it with and without the times). `finishedOnly` counts a thought as nothing finished. An answer kept before slice 20 has none and shows none, so `STORED_FORMAT` stayed 2: the new part only adds to what fits.
- **New text fades in** (slice 16, `chat/rich-text.tsx`): opencode's `markdown-word-enter` at 50c5fce, an opacity fade of 180ms (`.word-enter` in `src/app/globals.css`, only under `prefers-reduced-motion: no-preference`). Only an answer that came in after the conversation mounted fades (`shownAtFirst` in `chat/conversation.tsx`), never one it mounted with, such as a conversation brought back after a reload; this, not the chat's status, decides it, since an answer's last text can arrive in the same render that ends the answer. `RichText` keeps where each update's words begin (`starts`, in characters shown, React's "storing information from previous renders" pattern) and wraps each update's words in one span per run, so a reply that arrives in one piece, as on staging, fades as one and is still one text node for `getByText`; the fake model's words, one per 15ms, fade by groups. `Arrival` keeps from its mount whether it fades: the next update doesn't cut a fade short, and words mounted anew by a change of form (a table taking shape) don't fade again. Under reduced motion (`useReducedMotion`, `chat/use-reduced-motion.ts`, a `useSyncExternalStore` on `matchMedia`, which jsdom lacks, so there nothing asks for it) the text has no spans at all. The conversation stays out of any live region. axe reads a word mid-fade as low contrast, so `tests/e2e/accessibility.ts` finishes every fade while axe reads.
- **Tables** (slice 19, `chat/rich-text.tsx`; the parser in `src/lib/markdown.ts`, which only the browser uses): opencode's at 50c5fce (`docs/decisions.md`, Design, 2026-10-20): a real `<table>`, its header's named cells `<th scope="col">` in medium weight over `border-border-strong`, rows over `border-border`, both `0.5px` (Chromium draws 1px on a screen of 1x), cells `p-3 align-top`. Each cell is `min-w-36`, which Chromium honours on table cells, so a wide table scrolls rather than squeezing its columns to a word per line. Every row is padded to the widest row or the header with empty `<td>`s, so the hairlines run the full width; a header's empty name is a `<td>` too, as it names nothing, and a row or header of nothing but empty cells is dropped by the parser. The table sits in `SideScroll`, an `overflow-x-auto` box that a `ResizeObserver` measures, on itself and on the table: while the table is wider, the box is `role="region"`, named "Table, scrolls sideways", with `tabIndex={0}`, so the keyboard reaches it (axe's `scrollable-region-focusable`, which checks only a box that overflows); a table that fits adds no tab stop. A hidden Browser pane delivers the observer's first measure only when it next draws. The cells' runs are built in `RichText`'s render, not inside `SideScroll`, so the fade's character count (`words.at`) keeps the rendered order. The fake model writes no table, so `tests/e2e/chat.spec.ts` opens a kept conversation that holds two.
- **Stop** (slice 12): while the assistant works, the message box's Send button is Stop, one `<button>` whose label and type change, so focus stays on it; an empty Send is `aria-disabled`, not `disabled`, which would drop focus to the page. A Stop click calls `preventDefault()`: `useChat`'s `stop()` can end the answer and turn the button back into a submit button before the browser's default action, which then sent the draft (found 2026-10-20 by `tests/e2e/chat.spec.ts`; jsdom's `fireEvent` doesn't show it). `stop()` aborts the request, sets the status to `ready` and calls `onFinish` with `isAbort` (ai 7.0.143, `AbstractChat.stop` and `makeRequest` in `node_modules/ai/dist/index.js`, read 2026-10-20; the AI SDK's *Stopping Streams*, through Context7); `afterAnswer` marks the question as stopped only when `stopRequested` says the visitor pressed Stop, since "Start over" aborts too. The route hands the cancel to the model call (`request.signal`), so no further model calls follow; the call in flight is a whole reply, which Cloudflare may still finish and count.
- **A stopped answer** keeps its parts as they were: its text so far, its finished searches, any section it saved (the PRD keeps it). `stopped` holds the ids of the questions whose answers were stopped, so an answer stopped before its first part still says "You stopped this answer." under its question. A step still running reads as stopped ("Stopped searching the interviews for “…”", "Stopped checking the quotes in …", without a full stop, like the finished step lines), never as running or failed. What goes back to the server is trimmed in the transport (`prepareSendMessagesRequest`, `finishedOnly` in `workspace/stopped-answer.ts`): unfinished steps are dropped, and so is an answer that finished nothing; the server's format check would refuse a half-arrived tool call, and the model would see a call without its result.
- **The message box grows** with its text through `field-sizing: content`, from three lines (`min-h-24`) to 180px (`max-h-45`), then scrolls; Chrome 123, Firefox 152 and Safari 26.2 support it (MDN's compatibility data, read 2026-10-20 through Context7), and older browsers keep the three lines. A `ResizeObserver` keeps the chat on its newest message when the conversation's pane gets shorter, as the box grows or the suggestion shows, unless the visitor scrolled up; jsdom has none, so `tests/unit/setup.ts` stubs it.
- **Scrolling panes are `relative`:** Tailwind's `sr-only` is `position: absolute`. Inside a scrolling pane that isn't positioned, those labels are placed against the page, stretch it and make the whole page scroll (found 2026-10-18). The PRD pane is also focusable (`tabIndex={0}`), or axe reports `scrollable-region-focusable` before it holds a link.
- **Jump to latest** (slice 14): shows while the chat is 48px or more off its end (`FOLLOW_MARGIN`), after a scroll up or when the conversation grows without one (a `ResizeObserver` on the conversation's `<ol>`, which changes only the button, not whether the chat follows; in Chromium, opening a folded line while the pane gains its scrollbar instead resizes the pane, and the pane's own observer takes the chat to its end). It's the scrolling pane's last child, a zero-height `sticky bottom-0` box whose `-mt-6` cancels the `space-y-6` margin it gives the item before it (Tailwind 4 puts that margin on every child but the last, read 2026-10-20 through Context7), with the button absolute inside; so the pane stays `#chat-title + div` with the same children, which `tests/e2e/layout.spec.ts` measures. `hidden lg:block`, since a phone's chat doesn't scroll on its own. A click sets following, moves focus to the message box (or the chat's heading once the allocation is used up and the box is gone) before the button unmounts, and calls `scrollTo` with `behavior: "smooth"`, or `"instant"` under `prefers-reduced-motion: reduce` (MDN, `Element.scrollTo`, read 2026-10-20 through Context7). While that smooth scroll runs, its downward steps don't count as the visitor leaving the end (`jumping`); a step upward does. If the conversation grows meanwhile, as opened searches still sliding open do, the conversation's observer scrolls on to the new end instead of showing the button; before that, the jump stopped at the old end and stayed there, with no button (found 2026-10-21, `tests/e2e/layout.spec.ts`, 2 runs in 60). It has an opaque background, as it sits over the text. jsdom lays nothing out and has no `matchMedia` or `scrollTo`, so `tests/unit/workspace.test.tsx` gives the pane a size, stubs both and reports the conversation's resizes itself.
- **Only "See it" scrolls the PRD.** The chat follows its newest message unless the visitor scrolled up; on a phone, where the panes stack and don't scroll on their own, it doesn't follow.

## After a reload (`workspace/stored-conversation.ts`)
- **What's kept:** the whole conversation, in `localStorage` under `prd-assistant:conversation`, with `format` (`STORED_FORMAT`, 2 since slice 12 added `stopped`), `interrupted` and `stopped`, the questions whose answers the visitor stopped. The PRD isn't stored apart: it's rebuilt from the conversation, as always, and its chat quotes find their messages there. `Workspace` keeps it after every answer, finished or failed, never while one is on its way, and forgets it once the conversation is empty ("Start over", a failed first request). A browser that refuses storage or has no room keeps nothing, and nothing else changes.
- **Browser-only rendering:** `use(browser())` from `react-dom` (React 19.3) inside a `<Suspense>` whose fallback is the intro without its handlers. The server's page is that intro; in the browser the workspace's first render already holds what's kept, so `useChat` starts with it (`messages`) and nothing flashes between hydration and the restored view (https://react.dev/reference/react-dom/browser and Next.js's *Single-Page Applications* guide, "Rendering components only in the browser", read 2026-10-20 through Context7). The fallback's buttons are `aria-disabled` until then: they look the same, and Playwright waits for them instead of clicking into nothing.
- **A kept answer that broke off** (`interrupted`) shows as failed after the reload, with "Try again", until the next request, exactly as before it; sending a new message drops it first, as after any failure.
- **The check:** `restoreConversation` checks the stored form with Zod, synchronously, before the first render. It checks to the letter what the browser reads (a saved section, a search's passages, each part's type and state) and lets the rest through loosely; the server checks every message again when the next one is sent. A conversation that doesn't fit is removed, and the intro says "The PRD you started earlier couldn't be brought back: the demo has changed since. You can start a new one." until the visitor goes on. The schemas are held to the types in `src/lib` with `satisfies`, so a change there fails the typecheck. **Raise `STORED_FORMAT`** with any change that could stop an older conversation fitting: `ChatMessage`, the checked section, the parts the chat shows, or an upgrade of `ai`. A new kind of part that older conversations simply lack, such as the thinking times, doesn't need it.
- **Kept out of `src/lib`,** like the intro's logic, so the measurement's comparison doesn't report it.

## The download (`prd/prd-markdown.ts`)
- **Its form** (`docs/decisions.md`, Design, 2026-10-20): the title, the line under it and the explanation; all nine sections in order, one not drafted yet as "Not drafted yet."; each statement as a list item ending in "Sources: " and its names, each with a GitHub footnote (`[^1]`) holding that name's quotes, with the passage for an interview's and "(unverified)" for one the check couldn't confirm; under the statement, one nested item each, what the code objects to, in the PRD's words. Footnotes are numbered in the PRD's order.
- **The model's words are shown as written:** every Markdown mark inside a line is escaped, a mark that would start a heading or a list at the start of an item too, and line breaks become spaces.
- **Saving:** a `Blob` behind an object URL, clicked through an `<a download>` and freed right after the click, as MDN's example does (*JavaScript resource management*, read 2026-10-20 through Context7). The button shows once a section is saved.

## Copying a section (`prd/copy-section.tsx`, slice 17)
- **Its form** is opencode's copy button (`docs/decisions.md`, Design, 2026-10-21): 24px, a 14px grey icon, no border, `hover:bg-foreground/10` and `active:bg-foreground/20`, a sibling of the `<h3>` after it, so the heading's and the region's names don't change. It copies `sectionMarkdown` from `prd/prd-markdown.ts`: the download's form for one section, footnotes numbered within it.
- **When it shows:** the section is `group/section`; the button's wrapper is `opacity-0` under `@media (hover: hover)` and `opacity-100` on `group-hover/section` or `group-focus-within/section`, else always (a touch screen). Tailwind 4 already puts `hover:` and `group-hover:` inside `@media (hover: hover)` (upgrade guide, read 2026-10-21 through Context7). It stays clickable while transparent, as opencode's does.
- **Its label** (`.copy-tip` in `src/app/globals.css`) is CSS, `aria-hidden`: shown on `.copy-button:hover` after 0.4s, closed by `data-pressed` from the press until the pointer leaves, held open by `data-open` to say "Couldn't copy".
- **After a copy** the name is "Copied" or "Couldn't copy" for `COPY_OUTCOME_MS`, and an `aria-live="polite"` span says it once, since screen readers don't reliably announce a focused button's new name. Not `role="status"`: the chat's status line is the page's one. `navigator.clipboard.writeText` rejects when refused (MDN, read 2026-10-21 through Context7), and a page that isn't a secure context has no `navigator.clipboard`; both read "Couldn't copy". The desktop app's Browser pane refuses the clipboard while it's hidden, so a successful copy is seen only in the end-to-end tests there (found 2026-10-21).

## The scenario tour (`workspace/scenario-tour.tsx`, slice 24)
- **Only with `npm run dev:replay`:** `Workspace` renders it when `NEXT_PUBLIC_CHAT_REPLAY` was "1" at compile time, as the header's "Replaying recorded answers", so no build for staging or production has it, and neither does the end-to-end tests' replay server, which runs that build. It's a `fixed` `<aside>` over the page's corner, beside the intro or the workspace, never in their layout, so the layout tests measure nothing new.
- **What it sends:** a step's words, through `playScenario`, which leaves the intro as its button does and clears a pending check-in. A step counts as played once its words are among the visitor's messages (`playedScenarios` in `src/lib/scenarios.ts`), so the tour survives a reload and "Start over" begins it again; "Play next" offers the step after the furthest one played. Both are disabled while an answer is on its way.

## The intro (`workspace/intro.tsx`, `workspace/disclosure.ts`)
- **What shows when:** the intro until the visitor leaves it or the conversation holds messages (`conversationStarted`, which holds for a restored conversation too); the suggestion to try to break it once a section is saved, until the visitor has sent it (`breakItSuggestion`). Its button and the suggestion import their words from `src/lib/suggestions.ts`, never a copy: the measurement sends the same words, and changing them means a new baseline.
- **A failed first request:** `useChat`'s `onFinish` runs after every answer, once the error status is set, with `isError` and the messages from the chat's own state (ai 7.0.143, `makeRequestImpl` in `node_modules/ai/dist/index.js`, read 2026-10-19; the AI SDK's `useChat` reference through Context7). `afterAnswer` brings the intro back only when the intro's request failed before a section was saved, and clears the error, so the chat never opens on the old one. The server can send an error after a save (a reply cut off at its output limit, or the provider failing on the last call); then the section stays, with the chat's "Try again". Don't decide this in `onError`: it runs before the status is set, and the rendered `messages` can lag behind the chat's state. A ref marks the intro's request, so a later failure stays in the chat.
- **The message box's text lives in `Workspace`,** passed to `Chat`: the chat unmounts when the intro comes back, and what the visitor typed during a failed first request must survive. "Start over" leaves it, as before the intro.
- **Focus when the view changes:** `sendMessage` adds the message only after an await, so `flushSync` in the click can't place focus. The event names its target in a ref, and a layout effect keyed on the view focuses it once the new view has rendered: the chat's screen-reader heading after the button, the message box after the quiet way in, "Or ask your own question first", the intro's heading when it comes back. Not `useEffect`: for an update that isn't a click, such as a failed request, React runs a plain effect only after the browser paints, and until then focus sits on the page (React's `useEffect` caveats, read 2026-10-20 through Context7; found 2026-10-20 as a unit test that failed under load). The suggestion to try to break it unmounts with the button that has focus, so its click focuses the message box before it sends.
- **Not a named region:** the intro's heading mentions a "shared grocery list app", and the PRD is the region of that name; Playwright matches names as substrings, so a named intro would make `getByRole("region", { name: "Shared grocery list app" })` ambiguous.
- **Kept out of `src/lib`:** the intro's logic lives here, not in `src/lib`, whose changes the measurement's comparison reports as code that shapes the model (`src/server/measurement/report.ts`).

## When the AI can't answer (`workspace/quota.tsx`)
- **The used-up allocation:** `useChat`'s `onError` (`noteQuota`) sets `quotaUsedUp` when the error's message is `QUOTA_USED_UP` from `src/lib/chat.ts`, the server's words for Cloudflare's quota 429 (`src/server/AGENTS.md`). It lasts until a reload, through "Start over" too. The intro then shows `QuotaNotice` instead of its button and "Or ask your own question first"; the chat shows it instead of the suggestion, the message box and "Try again"; the PRD drops its check-in, which sends a message too. The conversation, the PRD and the link to the interviews stay.
- **The reset time:** 00:00 UTC, and the same moment in the visitor's locale and time zone (`nextReset`, `localTime`), computed in the browser when the notice first shows, so the server's render never holds a time.
- **Busy:** an error whose message is `DEMO_BUSY` shows those words with "Try again", since a minute later it can work. Every other error keeps the generic sentence.

## The source pop-over (`prd/source-popover.tsx`)
- **No library:** one native `popover="auto"` element serves every name. Each name is its invoker (`popoverTarget`, `popoverTargetAction="show"`), which gives light dismiss (a tap outside, Escape) and makes the name the pop-over's implicit anchor, so the CSS needs no `anchor-name` (MDN, *Using the Popover API*, "Popover anchor positioning", read 2026-10-18 through Context7).
- **Position** (`.source-popover` in `src/app/globals.css`): on a phone it isn't anchored, nearly full width and scrolling inside. From `lg` up it uses `position-area` with `position-try-fallbacks`, inside `@supports (position-area: bottom)`, with `inset` and `margin` reset as MDN advises, so browsers without anchor positioning get the centred box. Support (MDN's compatibility data, read 2026-10-18): Chrome 129, Firefox 147, Safari 26.
- **Highlighting** (`src/lib/highlight.ts`) reads a quote the way the check does, only to mark the words; whether a quote is confirmed is the check's call alone.

## Accessible names
- An `sr-only` span inside a button gets a space before it in Chrome's accessible name ("See it : Goals"), so a button whose name extends its visible text uses `aria-label`, starting with the visible words.
