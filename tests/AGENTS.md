# Tests: rules for working here

## The four layers
| Layer | Where | Tool | Tests | Run |
| --- | --- | --- | --- | --- |
| Unit | `tests/unit/` | Vitest, Testing Library, jsdom | Logic, validation, components | `npm run test:unit` |
| Integration | `tests/integration/` | Vitest against the local database | Real operations, from the operation to the database | `npm run test:integration` |
| SQL | `supabase/tests/database/` | pgTAP through the Supabase CLI | Grants, row-level security and constraints, as each role | `npm run test:sql` |
| End to end | `tests/e2e/` | Playwright against a production build on port 3100, and the same build replaying recorded answers on port 3101 | What a visitor sees, plus an axe accessibility check on every page | `npm run test:e2e` |

Every feature gets a test in each layer it touches. A bug fix starts with a test that fails without the fix.

## Fixtures and fakes
- **Fixtures are deterministic.** Unit tests build their own small data inline. Integration and end-to-end tests use the sample notes in `notes/`, which `db:start`, `db:reset` and `notes:load` put in the database. Every test leaves the database holding exactly those notes.
- **Fakes sit only at external boundaries.** That means the AI provider: the fake embedder (`src/server/ai/fake-embedder.ts`) and the fake chat model (`src/server/ai/fake-chat-model.ts`). The database is real in integration tests, never mocked.
- **The fake embedder counts shared words,** without stemming or synonyms ("notification" and "notifications" are different words to it). A search test's question uses the words of the passages it expects; search by meaning can only be checked on staging.
- **The fake chat model follows a script:** it searches with the visitor's whole message, then quotes the closest passage. A message with "draft" or "section" in it makes it save a section instead, the one the message names last (so the check-in, "Introduction / Overview looks right. Please draft Goals / Objectives.", drafts Goals / Objectives), or the first when it names none: one statement per closest passage (up to three) quoting the first sentence of its answer, and one quoting the message's first sentence, then a reply saying what the check found. `FAKE_SEARCH_AGAIN` makes it search again with the same words while the search is on offer (three times), so the chat folds its searches. `FAKE_FLAWED_SECTION` in the message adds three flaws for the check to catch: a quote from the researcher's question, another passage's words under the first passage's id, and a statement that cites nothing. A message containing `FAKE_FAILURES.beforeAnswering` or `FAKE_FAILURES.partway` makes it fail once, so a retry succeeds. Its memory of failed messages lasts as long as the server, so an end-to-end test adds `testInfo.testId` to its message. Unit tests pass their own `failedMessages` and `chunkDelayInMs: 0`.
- **The replayed answers** (`src/server/ai/replay-chat-model.ts`) run only on the second server of `playwright.config.ts`, port 3101, started after the first on its build with `AI_CHAT_PROVIDER=replay` and `REPLAY_SPEED=100`; only `tests/e2e/replay.spec.ts` goes there, and every other test stays on the scripted fake. That server gives each request's recordings out in turn, so a test there expects the first recording only once per run. Unit tests pass the replay their own `picks` and use fake timers for its waits. The scenario tour's steps (slice 24) answer there too, by their words; their scripted failures happen once per server process, so a test there that wants one sees it only once per run, and unit tests pass their own `failed`.
- **Next.js renders its own empty `role="alert"`** (the route announcer) on every page. Scope alert lookups to the part of the page under test.
- **`server-only`:** Vitest maps it to an empty module (`vitest.config.ts`), so tests can import server code.

## Writing tests
- **End-to-end selectors:** use roles, labels and stable ids such as `#daan-1` (`passageAnchor`).
- **Waiting:** wait for a visible condition (`await expect(locator).toBeVisible()`, `toHaveCount`), never a fixed time. Each check may take 15 seconds (`expect.timeout` in `playwright.config.ts`), since the fake model's paced answers ran past the default 5 under load (found 2026-10-21; Playwright's *Timeouts*, read through Context7). A longer wait is the fix only when the page was still on its way; a test that fails even at 15 seconds is waiting for something that never comes.
- **A step can show before its answer ends:** the fake model's save arrives before its reply's text, so a section's statements appear while the answer is still on its way, and the check-in stays disabled until it ends. Wait for the check-in to be enabled before clicking it, and before a reload that should keep the answer. The reply's last words show before the answer ends too, and until it ends the chat follows it to its end: a test that scrolls or opens something in a finished answer waits for the Send button first (found 2026-10-21, `tests/e2e/layout.spec.ts`, 1 run in 60). Playwright retries a click on a disabled button, and its retries scroll the target into view even when it was visible, which looks like the PRD scrolling by itself (found 2026-10-20 with `DEBUG=pw:api`: "element is not enabled", then "retrying click action").
- **New pages** get an `expectNoAccessibilityViolations(page)` check (`tests/e2e/accessibility.ts`). While axe reads, it finishes at once every animation and transition that ends, what arrives (`.arrive`, slice 25), the assistant's words arriving (`.word-arrive`, slice 26) and the pop-over growing in, those running and those that start meanwhile; the moving band never ends and is left alone. axe measured a word mid-fade as failing `color-contrast` in about one full run in two whenever a test checked while an answer's words still arrived (found 2026-10-21). Waiting for the fades to end first wasn't enough: in CI, words came after a pause, while axe was reading.
- **Measuring positions:** what arrives rises a few pixels as it comes (slice 25), so a test that measures where things sit finishes every animation that ends first, as `childGaps` in `tests/e2e/layout.spec.ts` does; the pop-over grows from 92% as it opens (slice 26), so a test that measures it finishes its opening first. Playwright counts an element at opacity 0 as visible, and waits for a moving one to be still before it clicks.
- **What moves for under a second** (slice 26): the words' spans are gone once the words have arrived, and so are the lines that fold, so a test that looked afterwards would find nothing. `recordArrivals` (`tests/e2e/motion.ts`) records what matches a selector as it's added, from an init script; the pop-over's tests record its `transitionrun` and `animationstart` events the same way. A role query finds no hidden element, so a test checks a closed pop-over's `display` by its id. The replay server picks a recording by the visitor's words and gives out a request's recordings in turn, and one of A's saves without a reply: a test that needs a long reply sends request B's words, read from `src/server/ai/replays.json`, never from the app. Once the app's suggestion changed, D's words in the app no longer matched its recordings, and the scripted fake answered word by word instead (found 2026-10-22 in CI).
- **Moving pieces in unit tests:** the words arrive and the searches draw together only where the browser lists its animations (`useMotion`, `src/features/chat/use-reduced-motion.ts`), and jsdom has no `getAnimations`, so there the text stays whole and the searches fold at once, as every other test reads them. A test of what moves defines `Element.prototype.getAnimations` itself and deletes it after, then fires `animationEnd` to end what it waits for.
- **The clipboard in end-to-end tests:** grant `clipboard-read` and `clipboard-write` with `test.use({ permissions })` and read it with `navigator.clipboard.readText()` in `page.evaluate`. On Windows the text comes back with `\r\n` line breaks, so the test normalises them and the exact text is pinned in a unit test (found 2026-10-21). A phone test that needs `(hover: none)` sets `hasTouch: true`; the viewport alone keeps hover (Playwright's `browsercontext-viewport-mobile.spec.ts`, read 2026-10-21 through Context7).
- **Pop-overs in unit tests:** jsdom has no Popover API and its stylesheet hides every `[popover]`, so `tests/unit/setup.ts` puts in a stand-in: `showPopover`, `hidePopover` and `togglePopover`, a click on a `button[popovertarget]` acting as its invoker, and the `toggle` event. It doesn't light dismiss, move focus back or match `:popover-open`; the end-to-end tests check those. An opened pop-over is the one `dialog` a role query finds.
- **`matchMedia` stubs** need `addEventListener` and `removeEventListener` too: `useReducedMotion` subscribes to the query's changes.
- **The home page opens on the intro.** An end-to-end test that starts in an empty chat clicks "Or ask your own question first", which sends nothing; the intro's button sends the fixed first request. That request can't hold a fake failure phrase, so its failure is tested by holding or aborting `/api/chat` with `page.route(..., { times: 1 })` (`tests/e2e/intro.spec.ts`), and in `tests/unit/workspace.test.tsx` with a stubbed `fetch` that answers with streams built by `createUIMessageStream` and `createUIMessageStreamResponse` from `ai`. The owner decided on 2026-10-20 to keep "Or ask your own question first" (`docs/decisions.md`, Design, the intro as built, 2026-10-19), so it stays the tests' way into an empty chat.
- **What the workspace keeps in `localStorage`** is written by a `useEffect`. After an update that came from the network (an answer, a failure, a stop), React may run it only after the browser paints, so the screen can show the result before anything is kept. A unit test that reads storage after such an update reads it inside `waitFor`, never right after a `findBy…` (found 2026-10-20 in CI: under load, the old reads failed 7 times in 30 runs, the waiting ones never).
- **Focus after a click in a unit test:** `fireEvent.click` dispatches the event without focusing the element, as a real click would, so a test that checks where focus goes afterwards calls `element.focus()` first (Testing Library, *Considerations for fireEvent*, read 2026-10-19 through Context7).
- **Playwright matches accessible names as case-insensitive substrings** unless `exact: true`, so a new heading or region must not contain an existing name the tests look up, such as the PRD's "Shared grocery list app".
- **Integration tests** need the local stack and `.env.local`: `npm run db:start`, then `npm run env:local`. Files run one after another because they share the database.

## Running one test
- Unit: `npx vitest run --project unit tests/unit/parse-interview.test.ts -t "rejects"`
- Integration: `npx vitest run --project integration tests/integration/load-notes.test.ts`
- SQL: `npx supabase test db supabase/tests/database/transcripts.test.sql`
- End to end: `npx playwright test tests/e2e/pages.spec.ts -g "home page"`. Install the browser once with `npx playwright install chromium`.

These direct commands skip the environment guard, so finish with the npm script for that layer.
